# Generalized mission-adaptive UAV interfaces — Schema 2.0

This project is a **research-prototype contract**, not a flight controller. It is a proposed generalization of the original Step 1 schema supplied with the mission-adaptive UAV roadmap. It follows three external modeling ideas:

- **PlanSys2/PDDL:** separate static goal/action knowledge from the dynamic world state, planner and executor; https://plansys2.github.io/design/index.html
- **W3C SOSA/SSN:** describe observations by subject/property/result, sensor provenance and observation time; https://www.w3.org/TR/vocab-ssn/
- **JSON Schema:** use a versioned validated boundary between computers; https://json-schema.org/specification

The project itself is **not** a normative PDDL, SOSA/SSN, or PlanSys2 implementation.

## Quick start

Requires Python 3.10+.

```bash
cd mission_adaptive_uav_schema_v2
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
python -m scripts.check_examples
python -m scripts.export_schemas
pytest -q
```

The baseline suite contains 23 tests. There are three independently valid mission pairs in `examples/`:

| Mission | Example goals | Demonstrated operator |
|---|---|---|
| `warehouse` | Find extinguisher, assess clear/blocked access, return | `EQ`, `ONE_OF`, `BINDING` |
| `exit_sign` | Find exit sign, read text, return | `EQ`, deferred inspection |
| `thermal_inspection` | Verify surface temperature <= 75°C, return | `LTE` numeric comparison |

## What is actually generalized

**MissionSpec** (`interfaces/spec.py`) changes only when the objective, its verification policy, or the available capabilities change. It contains:
- Mission identifier and revision, robot identifier;
- A goal dependency graph, goal priorities, and `ALL`/`ANY` evidence-rule composition;
- Subject selectors: `ENTITY`, `CLASS`, `BINDING`, `ROBOT`, `REGION`;
- Goal conditions: `EQ`, `ONE_OF`, `GTE`, `LTE`, `EXISTS`, with expected typed values;
- Allowed producer IDs, confidence thresholds and maximum observation age;
- A registry of advertised high-level action capabilities and allowed target categories.

**MissionSnapshot** (`interfaces/state.py`) is generated by the trusted onboard state builder or by the simulator. It contains:
- Version and state-sequence numbers;
- Robot pose and map version, entities, frontiers and viewpoint/region references;
- Goal progress, resolved entity bindings, timestamped observations;
- Remaining energy/time, reserve budgets and current return estimates;
- Concrete high-level action candidates and estimated *execute + return-from-predicted-endpoint* costs.

**PlannerDecision** only contains a selected action ID plus mission/state/map identity and an optional rationale. `validate_decision()` rejects unknown and stale actions. Flight-path feasibility and power safety are **not checked** by this package.

## Why entity bindings matter

A goal such as `find a fire extinguisher` initially references a **class**, not a nonexistent object ID. When a trusted detection verifies the goal, the onboard mission manager can bind `target_equipment` to the discovered instance `ext_2`. A later goal such as `assess access to target_equipment` then uses `BINDING`. This prevents a detection of extinguisher A from being combined with an inspection of extinguisher B.

For simplicity, this prototype permits bindings from goals with exactly one evidence rule. Goal verification checks that the bound entity is supported by valid goal evidence. A production implementation should define stronger multi-object/quantified goal logic and conflict resolution.

## Example: mission-specific semantics as data

```json
{
  "id": "access",
  "description": "Determine whether target access is clear or blocked",
  "depends_on": ["locate"],
  "priority": 1.0,
  "evidence_logic": "ALL",
  "evidence_rules": [
    {
      "id": "r_access",
      "subject": {"kind": "BINDING", "ref": "target_equipment"},
      "property": "access_state",
      "operator": "ONE_OF",
      "expected": ["CLEAR", "BLOCKED"],
      "min_confidence": 0.85,
      "allowed_producers": ["sim_geometry"],
      "max_age_s": 1800.0
    }
  ],
  "bind_entity_as": null
}
```

`BLOCKED` is a valid **verified finding**, rather than a verification failure. Whether this constitutes mission success depends on the mission's requested outcome, and the planner should not infer accessibility from a mere detection.

## Migrating from original Step 1

This is a deliberate **breaking v2 contract**, not an invisible update to v1:

| v1 | v2 |
|---|---|
| `MissionState.mission` free-form string | `MissionSpec.description` plus structured `goals` |
| `MissionTask.required_evidence.type = ACCESS_ASSESSED` | `EvidenceRule(property='access_state', operator='ONE_OF', expected=['CLEAR','BLOCKED'])` |
| `Evidence.outcome` string and task_id | `Observation(subject_id, property, value, producer_id, observed_at)` |
| `MissionTask.status` in combined snapshot | `GoalProgress.status` in dynamic snapshot |
| `CandidateAction.type` fixed enum | `CandidateAction.capability_id` referencing allowed spec capability |
| `target_kind` bound to fixed type | capability declares supported target kinds |
| `usable_energy_wh` | `remaining_energy_wh`, `remaining_flight_time_s`, explicit reserves |
| `state_seq/map_version` | both preserved; `spec_revision` added |
| `confidence` | still separate for detection vs frontier geometry |

For ROS 2 integration, keep the v2 snapshot as a compact **serialized interface**. Raw `/livox/lidar` and `/left_camera/image` data stay on the onboard side; the planner receives only summarized candidate/evidence structures (with optional artifact references).

## Important limits and work still needed

1. **No sensor authenticity.** An allowlisted `producer_id` in a JSON file is not authentication. The onboard state builder must own the producer registry, verify messages from trusted ROS 2 components, and prevent the LLM from constructing the snapshot or adding observations.
2. **Confidence is not guaranteed calibration.** Thresholds are illustrative, and different sensor confidences may not be directly comparable. Later work should introduce calibrated quality measures per producer and condition.
3. **No physical safety assurance.** Step 3 must recompute energy/time from the candidate endpoint, enforce reserves and collision/path constraints, and implement return/land fallback under disconnection.
4. **No automatic spec mutation.** Goal additions/changes are represented by incrementing `MissionSpec.revision`; this package does not implement approval, patching or rollback. Mission changes must come through an authorized mission manager, not arbitrary LLM-written state.
5. **No inference of objective status.** The functions validate **claims** of verified goals. The trusted onboard state machine must build and update those claims using raw sensor data and verified evidence. There is no automated `PENDING -> VERIFIED` operator here.
6. **No universal safety/resource vocabulary.** The prototype handles energy and time only; communication budgets, battery voltage under load, localization uncertainty, emergency landing sites and risk models can be added as typed contracts once an actual use case demands them.
7. **No logic over arbitrary groups.** `ALL` and `ANY` represent small conjunction/disjunction rules; quantifiers, temporal conditions, negative evidence and composite plans require a richer formalism, potentially PDDL/PlanSys2.
8. **No secure multi-robot or distributed consistency handling.** Sequencing and version matching are local consistency checks. Retries, replay protection, clock synchronization, authority and state reconciliation remain future work.

## Source notes

The research roadmap explicitly calls for structured missions, evidence, resource estimates, candidate actions, and a stable simulation/ROS 2 bridge. The v2 design extends the roadmap to support different missions **without rewriting code**; these extensions are recommendations, not text quoted from the original documents. The first reference uses conventional symbolic planning concepts, while the second provides a vocabulary for observations. This implementation intentionally remains a small Python-specific contract rather than adopting the entire standards.
